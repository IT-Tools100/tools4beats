# VERSE ALTERNATIVE
## Техническое задание на разработку настольного приложения для битмейкера

**Цель:** создать собственное настольное приложение для поиска музыкальных артистов, управления контактами, автоматизации коммуникаций, продажи битов и контроля сделок.

**Основной референс:** Verse by 1vremennobeats, версия 5.9.0.

**Пользователь:** один битмейкер, использующий приложение для личного бизнеса.

**Основная платформа:** macOS на Apple Silicon, с возможностью дальнейшей поддержки Windows.

**Среда разработки:** OpenCode + DeepSeek V4.1 Flash.

**Принцип разработки:** сначала рабочая архитектура и основные функции, затем постепенное добавление интеграций. Не создавать фиктивные функции и интерфейсы, которые ничего не делают.

---

# 2. ТЕХНОЛОГИЧЕСКИЙ СТЕК

Предпочтительный стек:

- Python 3.12 или совместимая стабильная версия.
- PySide6 для настольного интерфейса.
- PostgreSQL для хранения данных.
- SQLAlchemy 2.x для работы с базой данных.
- Alembic для миграций.
- Pydantic для валидации данных.
- httpx для HTTP-интеграций.
- asyncio для асинхронных задач.
- pytest для тестирования.
- FFmpeg для работы с аудиофайлами при необходимости.
- Отдельные адаптеры для внешних сервисов.
- API языковых моделей для AI-функций.

На первом этапе приложение должно работать локально на MacBook Air M1 с 8 ГБ RAM.

Не использовать Kubernetes, микросервисы, несколько баз данных или сложную инфраструктуру без реальной необходимости.

PostgreSQL можно запускать локально через Docker. Приложение должно запускаться одной понятной командой после первоначальной настройки.

Предусмотреть конфигурацию подключения к базе данных через переменные окружения.

Секреты и токены хранить отдельно от исходного кода. На macOS по возможности использовать Keychain.

# 4. INSTAGRAM DISCOVERY

Создать модуль поиска артистов, аналогичный ReachVerse.

- плейлисты и связанные с ними публичные страницы;

## 4.2. Типы поиска

Предусмотреть отдельные стратегии поиска:

- анализ публикаций и Reels;
- анализ публичных отметок;
- поиск по доступным данным подписчиков;
- поиск по доступным данным подписок;
- проверка уже известного списка профилей;
- поиск по публичным хештегам;
- поиск по географическим признакам, если источник предоставляет соответствующие данные;
- поиск по лайкам и комментариям, если это разрешено и технически доступно.

Недоступные операции должны отображаться как неподдерживаемые, а не имитироваться.

## 4.3. Фильтры

- артисты;

- другие категории;

- источник обнаружения;

- уже добавленные контакты;
- исключённые профили.

## 4.4. AI-классификация

- Media.
- Other.

Классификация должна учитывать доступные описания, публикации и музыкальные ссылки.

- дату анализа;
- модель, использованную для анализа;

Не останавливать весь поиск, если AI API временно недоступен. Сохранять найденные данные и помещать необработанные профили в очередь повторного анализа.

## 4.5. Защита от повторного сбора

Сохранять историю обработанных:

- источников;
- публикаций;
- профилей;
- отметок;
- поисковых заданий.

Если задача остановлена, при повторном запуске продолжать с последней сохранённой позиции.

Повторно обнаруженный профиль не должен создавать новую карточку.

Добавить кнопки:

- Start.
- Pause.
- Resume.
- Stop.
- Clear Search History.
- Clear Results.
- Export.
- Import to CRM.

Поддержать ручное добавление, массовую вставку и импорт TXT.

Не реализовывать обход CAPTCHA, взлом авторизации, кражу сессий или скрытый обход ограничений платформ.

Если доступ к Instagram невозможен, интерфейс должен объяснять причину и предлагать импорт данных из CSV либо другой доступный источник.

Использовать уникальные идентификаторы каналов.

Если контакт уже существует, обновлять его данные, а не создавать новую карточку.

При обнаружении нескольких потенциальных совпадений показывать интерфейс ручного объединения.

Объединение должно сохранять историю сообщений, сделки, заметки и источники.

- фактически полученные деньги;
- потенциальную сумму сделки;
- валюту;
- дату платежа;
- историю изменений;

Создать единый модуль кампаний с отдельными адаптерами для каждого канала.

Поддержать переменные:

Состояния:

- Draft.
- Queued.
- Running.
- Paused.
- Completed.
- Failed.
- Cancelled.

Кнопки:

- Start.
- Pause.
- Resume.
- Stop.
- Retry Failed.
- Export Results.

Повторный запуск не должен отправлять сообщения тем же получателям без явного разрешения пользователя.

## 7.5. Проверка результата

Разделять:

- запланировано;
- попытка отправки;
- отправлено;
- подтверждено каналом;
- доставлено, если это подтверждает канал;
- ошибка;
- пропущено.

Не обозначать сообщение доставленным только на основании успешного вызова API или нажатия кнопки отправки.

## 7.6. Повторные сообщения

Follow-up должен иметь отдельные списки и историю.

Пользователь выбирает получателей и задаёт последовательность сообщений.

Перед отправкой исключать:

- ответивших контактов, если статус или данные переписки указывают на ответ;
- контакты с Do Not Contact;
- контакты без подходящего канала;
- контакты, которые уже получили эту последовательность.

Не предполагать, что ответ артиста всегда можно обнаружить автоматически. Если канал не предоставляет историю или события входящих сообщений, предусмотреть ручную отметку ответа.

- дате последнего контакта;
- наличию email;
- наличию телефона;
- сумме покупок;
- наличию сделки;
- признаку Do Not Contact.

## 9.4. Надёжность

Каждая автоматизация должна иметь:

- уникальный ID;
- название;
- расписание;
- условия;
- действия;
- состояние;
- журнал запусков;
- результат;
- сообщение об ошибке.

Предотвращать повторное выполнение одного и того же события.

Если отправка не удалась, не менять статус на успешно обработанный.

Повторные попытки выполнять с ограничением количества и контролируемой задержкой.

# 10. BEAT SERIES

Создать систему последовательной отправки бит-паков.

Пример:

День 1 — первая подборка из 3 битов.

День 3 — вторая подборка.

День 6 — третья подборка.

Настройки:

- список контактов;
- список паков;
- текст для каждого этапа;
- интервал между этапами;
- канал;
- расписание;
- условие остановки;
- журнал отправки.

Каждый пак может содержать несколько битов.

Карточка бита должна хранить название, ссылку на прослушивание, жанр, BPM, тональность и лицензионные условия.

Поддержать до 30 этапов серии как конфигурируемый предел, а не жёсткое архитектурное ограничение.

Ответивших клиентов и контакты с Do Not Contact исключать из дальнейших отправок в соответствии с настройками сценария.

# 11. SCHEDULE

Создать общий планировщик.

Поддержать:

- разовые задания;
- повторение по дням недели;
- выбор времени;
- часовой пояс;
- дату начала;
- дату окончания;
- паузу;
- ручной запуск.

Расписание должно поддерживать кампании, CRM-автоматизации, сбор доступных данных и мониторинг размещений.

В интерфейсе показывать ближайшие задания, последние запуски и ошибки.

Если компьютер выключен, приложение не должно делать вид, что задача выполнилась.

После запуска проверять пропущенные задания и предлагать продолжить их в соответствии с настройками.

# 12. AI ASSISTANT

Создать встроенного AI-помощника.

## 12.1. Режим Help

Помогает:

- разбираться в интерфейсе;
- объяснять функции;
- анализировать ошибки;
- искать нужные настройки;
- объяснять журнал действий;
- формировать рекомендации.

## 12.2. Режим Deals

Пользователь прикрепляет до четырёх скриншотов переписки или описывает ситуацию.

ИИ:

- анализирует контекст;
- определяет предполагаемую потребность артиста;
- предлагает ответ;
- объясняет логику ответа;
- предлагает следующее действие;
- может предложить напоминание.

Предусмотреть возможность прикрепления конкретного контакта из CRM.

## 12.3. Управление приложением через ИИ

ИИ может предложить:

- создать шаблон;
- заполнить поля кампании;
- подготовить список получателей;
- изменить статусы;
- создать напоминания;
- подготовить серию битов;
- сформировать отчёт.

Любые действия, связанные с отправкой сообщений, удалением данных или массовым изменением записей, требуют явного подтверждения пользователя.

ИИ не должен иметь прямого доступа к SQL-консоли или выполнять произвольный код.

Для взаимодействия с приложением использовать заранее определённые типизированные команды.

## 12.4. Работа с ошибками

Разрешить прикрепление журналов.

Перед передачей данных внешней модели удалять секреты, токены, пароли и ненужные персональные данные.

Историю чатов хранить локально, с возможностью удаления пользователем.

Результат автоматического сравнения считать кандидатом, а не доказательством использования бита.

# 23. КРИТЕРИИ ГОТОВНОСТИ

Функция считается готовой, если:

- существует реальный рабочий интерфейс;
- данные сохраняются;
- предусмотрена обработка ошибок;
- реализованы необходимые проверки;
- написаны тесты;
- функция интегрирована с общей CRM;
- нет фиктивных результатов;
- есть инструкция по настройке;
- пользователь может проверить её работу самостоятельно.

Не считать модуль готовым, если создана только кнопка или демонстрационная таблица.

# 24. ПРАВИЛА РАБОТЫ ИИ-РАЗРАБОТЧИКА

Перед изменениями изучить существующий проект.

Не переписывать рабочие модули без необходимости.

Не создавать дублирующие сущности и параллельные архитектуры.

Не менять зависимости без объяснения причины.

Не удалять пользовательские данные при миграциях.

Не добавлять секреты в исходный код.

Не реализовывать фиктивные интеграции.

Если внешний API не позволяет выполнить функцию, документировать ограничение и предложить альтернативу.

Работать небольшими завершёнными этапами.

После каждого этапа:

1. Запустить тесты.
2. Исправить ошибки.
3. Проверить интерфейс.
4. Обновить документацию.
5. Указать, что реализовано.
6. Указать, что ещё не реализовано.
7. Предложить следующий конкретный этап.

Не переходить к следующему большому этапу, если текущий не запускается или имеет критические ошибки.
